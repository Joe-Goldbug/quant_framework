## 二、为什么会反着来：一个可解释的机制

这不是随机噪音，有一个干净的解释：

> **字段的拥挤度是信号强度的结果，不是原因。**

一个字段之所以有 55 条存量 Alpha，正是因为它在 GLB 上真的能预测收益，所以被反复使用。一个字段之所以 0 条 Alpha，很可能是因为**试过的人发现它没用**——1138 个零使用字段里，绝大多数是「冷门且无效」，而不是「冷门且待发掘」。

更具体地看 `Cluster Test` 的反转：Cluster Test 度量的是**你的 Alpha 收益序列与同簇 Alpha 收益序列的相关性**。当信号很弱时，你的收益主要由通用风险因子（市值、行业、波动）驱动，而这些因子人人都暴露，所以相关性反而高。**弱信号必然高相关**。蓝海字段做出的是弱信号，因此 Cluster 低。

**结论**：`alpha_count`（字段流行度）与 `ProdCorr`（Alpha 收益相关性）是两个不同的量，二者甚至可以反向。用前者去优化后者，方向错了。

## 四、对「降 ProdCorr」这件事的诚实结论

必须说清楚一个限制：**ProdCorr 在回测阶段无法测量**，平台返回的是 `pending`，只有正式提交后才计算。你提供的 0.8324 / 0.7231 来自平台 UI，我无法在本地复现或优化它。

因此「降低 ProdCorr」这个目标，在提交前只能用 **Cluster Test** 作为代理。而本轮 20 条蓝海实验把这个代理指标从 0.75 压到了 0.39——**方向完全相反**。

真正能压 ProdCorr 的手段，按证据强度排序：

1. **提高信号强度**，而不是换字段。Sharpe 1.75 的因子天然比 Sharpe 1.0 的因子更独特，因为它的收益更多来自特质部分而非通用风险暴露。这是本轮最重要的反直觉结论。
2. **改变收益的时间结构**，而不是字段。同一批字段上，`ts_zscore` 归一化把 Cluster 从 0.74 拉到 1.20（`2rAqKQPb`），这是全campaign最好的 Cluster 成绩——**同样的拥挤字段，不同的时序拓扑，相关性差一倍**。
3. **换资产类别或区域**，让收益来源与生产库不在同一风险谱系。
